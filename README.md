# Tannery Desk

A digital leather sourcing platform. Buyers describe what leather they need, matching verified factories send quotations, the buyer picks one, pays, and follows the order through production, quality check, dispatch and delivery. The Tannery Desk team (admin) verifies factories and oversees everything.

> **Status:** the code was written and statically checked (syntax, imports, undefined names) but **has not yet been run against a live Django/PostgreSQL install**. Run the steps below, then `python manage.py test`, and fix anything your environment surfaces. Migrations are generated by `bootstrap.sh` on your machine (see "Database migrations").

## 1. Features

**Client** – register/login/logout, forgot/reset password, profile · browse the catalog with working filters and a detail popup · requirement wizard (12 steps, progress bar, summary with "Change" buttons, unique RFQ number, duplicate-submit protection, file attachments) · compare quotations side by side (price, MOQ, lead time, certifications, rating, "Recommended", "Lowest price", "Fastest") · accept/reject quotations · pay advance and remaining amount (Razorpay or sandbox) · track order on a timeline with progress, latest update and expected dates · message the factory · raise a dispute · review the factory.

**Factory** – register, profile and capability form, certificate upload, verification status · dashboard (new/relevant RFQs, quotations, orders, production) · accept/decline RFQs, send/edit/withdraw quotations · post production updates (started, progress %, quality check, packaging), mark ready for dispatch, dispatch with courier and tracking, change expected delivery, upload order documents · manage own catalog products.

**Admin** – dashboard (clients, factories, active RFQs/orders, pending verification, payments, recent activity) · approve/reject/suspend factories · suspend/reactivate users · RFQs (assign a factory manually), orders, payments, products (hide/show), disputes (status + resolution), basic reports · full Django admin at `/admin/`.

**Platform** – factory matching score, notifications (bell + page), one search box (products, factories, RFQs, orders), role-based access, private file storage, friendly error messages, loading/empty/success/error states, responsive layout (tables become cards on phones).

## 2. Technology

Django 5 · Django REST Framework · SimpleJWT · PostgreSQL · Razorpay · plain HTML/CSS/JavaScript (ES modules, no build step) served by Django.

## 4. Installation

Requires Python 3.11+ and PostgreSQL 14+.

```bash
cd tannery-desk
python -m venv .venv                 # 5. virtual environment
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r backend/requirements.txt
cp .env.example .env                 # then edit it (see section 7)
```

## 6. PostgreSQL setup

```sql
CREATE USER tannery WITH PASSWORD 'choose-a-password';
CREATE DATABASE tannery_desk OWNER tannery;
```
Put the same values in `DATABASE_URL` in `.env`. (If `DATABASE_URL` is empty the app falls back to a local SQLite file, only meant for a quick look.)

## 7. Environment variables (`.env`)

| Name | Meaning |
|---|---|
| `SECRET_KEY` | Long random string. Required when `DEBUG` is off. |
| `DEBUG` | `True` for development, `False` in production. |
| `ALLOWED_HOSTS` | Comma-separated host names. |
| `DATABASE_URL` | `postgres://user:password@host:5432/dbname` |
| `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET` | Leave empty for the sandbox. Secret stays on the server only. |
| `RAZORPAY_WEBHOOK_SECRET` | Optional; enables `/api/payments/webhook/`. |
| `ADVANCE_PERCENT` | Advance share of an order, default 30. |
| `EMAIL_*`, `DEFAULT_FROM_EMAIL` | Password-reset email. Default prints to the console. |
| `FRONTEND_URL` | Base URL used in password-reset links. |

## 8–10. Migrations, demo data, running

```bash
cd backend
./bootstrap.sh          # makemigrations + migrate + seed_demo + check
python manage.py createsuperuser   # optional: your own admin (role is set to ADMIN automatically)
python manage.py runserver
```
Open **http://localhost:8000**. The backend and frontend run as one server: Django serves `frontend/` (pages at `/`, assets at `/static/`, API at `/api/`). There is nothing separate to start for the frontend.

**Database migrations:** `bootstrap.sh` creates them on your machine. Commit the generated `*/migrations/` folders. Later model changes: `python manage.py makemigrations && python manage.py migrate`.

**Demo data:** `python manage.py seed_demo` (add `--reset` to rebuild). Everything it creates is flagged as demo (`[DEMO]` in names, `is_demo` on users).

## 15. Razorpay

- **No keys (development only):** with `DEBUG=True`, payments run in a labelled **sandbox**. The checkout is a test dialog; the server still verifies an HMAC signature before marking anything paid. No money moves. With `DEBUG=False`, both Razorpay keys are required and startup fails closed if either is missing; sandbox payments are unavailable.
- **Test or live keys:** put `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET` in `.env` (use `rzp_test_…` keys from the Razorpay dashboard first). The server creates the Razorpay order and checks the payment signature; the browser only gets the public key id. Sandbox endpoints switch off automatically.
- Optional webhook: in the Razorpay dashboard add `https://your-domain/api/payments/webhook/` for `payment.captured` and `payment.failed`, set a secret, and put it in `RAZORPAY_WEBHOOK_SECRET`.
- Amounts are always calculated by the server from the accepted quotation.

## 16. Production notes

- `DEBUG=False`, a real `SECRET_KEY`, `ALLOWED_HOSTS`, HTTPS (cookies are marked secure; `BEHIND_PROXY=True` behind a TLS proxy).
- `python manage.py collectstatic` (WhiteNoise serves static files); run with `gunicorn config.wsgi` from `backend/`.
- Uploaded RFQ files, order documents, certificates and message attachments go to `backend/private_media/` and are only served through permission-checked API downloads. Product photos go to `backend/media/` and need a web-server rule (nginx `location /media/`) or object storage in production.
- Back up PostgreSQL and `private_media/`.
- Sign-in uses a 15-minute access token kept in memory and a 7-day refresh token in an HttpOnly cookie. Throttling: 10/min on auth endpoints, 30/min on uploads, 20/min on payments.
- Delete demo accounts; create your own admin with `createsuperuser`.

## Render deployment

The root `render.yaml` creates one Python web service and a PostgreSQL database. In Render, create a Blueprint from the GitHub repository and deploy it. Fill in the unsynced host/origin values with the service's `*.onrender.com` hostname (origins include `https://`), and provide Razorpay credentials before the production service starts. `RENDER_EXTERNAL_HOSTNAME` is also used to allow the service hostname automatically.

The web service's filesystem is temporary by default. To retain uploaded product images and private files across deploys, attach a persistent disk and set `MEDIA_ROOT` and `PRIVATE_MEDIA_ROOT` to directories on that disk (for example `/var/data/media` and `/var/data/private_media`). Free services may sleep; use a paid web-service and database plan for production availability and persistence.

## Business rules worth knowing

- Factories only receive RFQs once **verified**; suspended users cannot sign in and their tokens stop working.
- Matching score (max 100): leather type 25 (required), application 20, MOQ 15, certifications 10, lead time 10, thickness 5, color 5, location 5, capacity 5. Minimum 40; top 10 factories receive the RFQ. Admin can also assign a factory by hand.
- "Recommended" quotation = 60% fit + 30% price + 10% rating.
- Accepting a quotation closes the other quotations, creates the order and notifies both sides. Advance = `ADVANCE_PERCENT` of the total; production updates unlock after the advance is paid; the remaining amount is payable from the Packaging stage; the client can complete the order only after full payment.
- Factories do not see who the buyer is until an order exists; clients do not see factory contact details until an order exists.
